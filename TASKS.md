# TASKS.md — publishing `@fllstck/mlayax` 0.1.0

Everything needed to turn the working MLX/TypeScript Laya port into a clean, published 0.1.0.
Written to be picked up cold in a new session: it names the source material, the pinned versions,
the numbers that define "correct" and "fast enough", and the hazards that already bit us once.

---

## 0. Goal and the reasoning to follow

Publish a **Laya typed-decision runtime for Node and Bun on Apple Silicon**, in TypeScript, on MLX —
with no Python, no pyproject, no subprocess. Two packages, published manually:

| package | contents | size target |
|---|---|---|
| `@fllstck/mlayax` | TypeScript/JS only: prompt construction, calibration, answer shaping, MLX runtime layer (vendored JS), request batching, HTTP service | < 300 KB |
| `@fllstck/mlayax-darwin-arm64` | native payload: `node_mlx.node` + `libmlx.dylib` + `libjaccl.dylib` + `mlx.metallib` + `SHA256SUMS` + `VERSION` | ≈ 64 MiB gzipped (metallib is 181 MiB raw) |

### The decision this follows (already argued; do not relitigate)

**Fork the artifact, not the package name.** We depend on a *patched* `@frost-beta/mlx` built against
a current MLX. We do **not** publish a general-purpose MLX binding under our own name; we ship our
runtime inside our product's platform package. Evidence behind this:

- `@frost-beta/mlx` 0.4.0 was last published **2025-04-19** and vendors MLX 0.25 (1.9x slower than
  0.32). It is not maintained.
- Every maintained alternative is **FFI over mlx-c** (`@johnhenry/backend-mlx`, `@nielspeter/mlx-ts`,
  `mlx-bun`). Measured: a maintained FFI port (`@johnhenry/laya` 0.3.2) runs **3.1x slower** than our
  NAPI binding on identical inputs (183.5 ms vs 59.1 ms for 16 rows), and its `compile` option buys
  3 % against our 12 % — because an FFI binding still issues every op from JS, so `mlx_compile`
  cannot remove the call overhead.
- `@mlx-node/core` (MIT, active, self-contained prebuilt) is model-shaped: no fused
  `rope`/SDPA/`layerNorm`, no generic safetensors reader, no compile. Adopting it means hand-writing
  the performance-critical parts.
- Therefore: keep a compiled binding (ours), own the artifact, publish it as a platform package.
  File the patch upstream as goodwill; if upstream revives, dropping the fork is a dependency swap.

### Explicitly out of scope for 0.1.0

WebGPU/CPU backends, ONNX backend, browser support, embedding shortlist, quantized checkpoints,
training, the Snake demo, Windows/Linux, Intel Macs. Note them in the README as roadmap.

Three notes on decisions taken inside this phase:

1. **attw runs with `--profile esm-only`, deliberately.** Under the default `node16` profile attw
   *fails* (exit 1) on `CJSResolvesToESM`, because the façade is ESM-only on Node ≥ 22 (`import`
   condition only, no `require`). That is the intent, not a bug, so the profile states it rather than
   suppressing it: the CJS row still appears, marked “ignored per resolution”. Adding a CJS build to
   turn that row green is not worth the dual-package hazard for 0.1.0. (A useful lesson recorded
   here because it cost a detour: piping a command into `tail` and reading `$?` reports *tail's* exit
   status, so a failing gate can look green — the first run of `check:attw` did exactly that.)
2. **`LICENSE`/`NOTICE` are committed copies,** not generated at pack time. The platform package is
   required to have **no scripts** (§5), so it cannot prepack them into place. `npm run verify` runs
   `scripts/sync-licenses.mjs --check`, which fails on drift — so the copies cannot go stale silently.
   Phase 8 must still add `licenses/` (full MLX + node-mlx texts) to the platform package.
3. **`.github/workflows/ci.yml` is deferred to Phase 7,** deliberately: every job it will contain
   depends on artifacts that do not exist yet, so a workflow written now could only be decorative.
   It is the one file in §3's layout that is intentionally absent.

### Phase 3 — MLX runtime (`src/mlx`) inside `@fllstck/mlayax`

- [ ] Decide vendoring: **default = vendor node-mlx's MIT `dist/` JS layer** as-is (proven), with a
      task noted for a slim wrapper later. Keep `vendor/node-mlx/LICENSE` and add it to `NOTICE`.
- [ ] Binary resolution: node-mlx's JS loads `build/Release/node_mlx.node`. Point it at the platform
      package instead (patch the resolution or shim `require`), and **test on Node and Bun**.
- [ ] Port `model.ts` + `agent.ts`. Preserve and comment these hard-won behaviours:
      - all scalar constants created in the activation dtype (`mx.array(1, x.dtype)`); a bare JS `0`
        in `mx.maximum(intArray, 0)` breaks the gather, and a bare `1`/`2`/`sqrt(2)` silently upcasts
        fp16 → fp32 for the rest of the graph (**20 % cost**). Add a test that asserts the dtype of
        the gelu output is f16.
      - weights pre-split at load (QKV/MLP/in_proj) — required for shape-polymorphic graphs and it is
        the reason `mx.compile(shapeless)` is even an option;
      - `takeAlongAxis(h, expandDims(pos, -1), 1)` for markers (`mx.take` with a `[b,count]` index
        prepends the batch dim → `[b,b,count,H]`);
      - attention masks built **outside** the compiled region, cached by `(b, L, row lengths)` — and
        **never disposed** (disposing a just-cached mask crashes with a bare `std::invalid_argument`);
      - top-2 features via `max` + tie-aware `where` (no slicing, so the graph stays polymorphic);
      - `mx.compile(fn, /*shapeless*/ false)` is the **default** (12 % win, one trace per shape);
        `shapeless: true` requires manual fp32-accumulating attention and costs 12–15 % — keep it as an
        opt-in (`MLAYAX_SHAPELESS=1`), documented;
      - `mx.tidy` default on for the sync path, **off** on the async service path (dispose feeds
        explicitly).
- [ ] Hugging Face loading (new work, see Phase 3b):
      `load("aac6fef/laya-mlx")` with disk cache, `HF_TOKEN`, `HF_HOME`, offline mode, revision pin,
      and per-file checksum verification. Weights are ~803 MiB and must never be bundled.
- [ ] Fail fast on: non-darwin, non-arm64, MLX version/metallib mismatch, missing fused symbols.
- [ ] Acceptance: `load()` from a local directory and from the Hub cache both work; a single
      `predict()` returns the fixture answers; run it under Node and Bun.

## 8. Hazards to encode as tests (all of these already cost us time)

1. **JS scalars upcast fp16 to fp32.** `mx.array(1)` is float32; mixing lifts the rest of the graph
   (~20 % cost, no error). Test: gelu/relu output dtype, and a bench ceiling.
2. **`mx.maximum(intArray, 0)`** returns float32 and the gather then rejects it. Test: the marker
   gather path with an int32 index tensor.
3. **`mx.take(h, pos, 1)` with a `[b, count]` index prepends the batch dim.** Test: markers shape.
4. **Disposing a just-cached attention mask** → crash on the next cache hit. Test: two identical
   forwards in a row, plus one with a different length.
5. **`fast.sdpa` is not shape-inferable** (bakes the traced shape) and **`Slice`/`Split` are not
   shape-inferable either**, so `shapeless` requires manual attention. Test: the shapeless profile
   produces the same answers as the default one on two different lengths.
6. **MLX build mixing**: two `libmlx` builds in one process collide on
   `@rpath/libmlx.dylib` and die with a symbol mismatch. Test: the load-time guard; document it.
7. **MLX build quality**: the metallib size class predicts throughput (190 MB fast vs 135–137 MB
   slow). Test: assert the shipped metallib sha256/size and gate on the bench.
8. **Prompt rendering regressions**: `labels` ignored for `noul` (the `@johnhenry` bug), labels
   rendered as `label: null` (our bug), Python JSON separators. Test: exact rendered strings **and**
   token ids from the frozen fixture tokenizer.
9. **`mx.tidy` around `mx.asyncEval`** is unsafe; the service path must dispose feeds explicitly.
   Test: repeated service batches under load, assert no crash and stable RSS.
10. **Rounding**: Python `round` is banker's; answer fields are 4-decimal. Test: tie values.

## 9. Open decisions (pick one and record the reason in the PR/commit)

| decision | options | recommendation |
|---|---|---|
| how MLX is obtained for the shipped artifact | (a) link a prebuilt MLX from a Python wheel; (b) build MLX in CI with Xcode | (a) for 0.1.0 (works without Xcode, fastest measured build); revisit (b) with the bench gate for provenance |
| vendored JS layer vs slim wrapper over the addon | (a) vendor node-mlx `dist/`; (b) ~300-line wrapper over the patched `.node` | (a) for 0.1.0 (proven); (b) as a follow-up to shrink the surface |
| one package or two | (a) façade + platform; (b) façade + platform + core | (a) — fewer manual publishes; core stays internal |
| `compile` default | specialized (default) vs shapeless | specialized; shapeless opt-in via env, documented trade-off |
| download-at-first-use vs bundle weights | — | download (they are ~803 MiB and Apache-2.0; never bundle) |

### Decided (2026-10-06, during Phase 1)

Every recommendation above is accepted. The reasons in one place, so they are not relitigated:

- **MLX for the shipped artifact → (a) link a prebuilt MLX from a Python wheel.** Forced rather than
  merely favoured: this machine has CommandLineTools only, so there is no Metal compiler and MLX
  cannot be built from source here at all. It is also the faster option (the wheel's 190 MB metallib
  beats Homebrew's 137 MB class by ~35 % on this workload). Note the spike's addon is rpath'd at an
  absolute venv path pointing into `site-packages/mlx/lib`; Phase 5 must replace that with a
  `@loader_path`-relative path, and the spike's current rpath is evidence of exactly the hazard §5
  and §8.6 describe. Mode (b) stays as a CI provenance experiment behind the bench gate.
- **Runtime layer → (a) vendor node-mlx's MIT `dist/` JS as-is.** Proven, and every number in §2 was
  measured through it. A ~300-line slim wrapper over the patched `.node` is the follow-up that
  shrinks the surface. `vendor/` is excluded from Biome and from TypeScript so it stays untouched
  until then.
- **Packaging → (a) two packages** (façade + platform). Fewer manual publishes, and `core`/`service`
  are internal source folders anyway, so they need no publish step to be tested.
- **`compile` → specialized by default,** shapeless behind `MLAYAX_SHAPELESS=1`. Retraces are one-off
  and amortise in a service; the 12–15 % shapeless tax is paid on every request.
- **Weights → download at first use.** ~803 MiB and Apache-2.0; never bundled, in either tarball.
  `.gitignore` already excludes `models/` and the HF cache.

Deliberately left open, because Phase 5 has to measure it: whether `node_mlx.node` should statically
link `libmlx` or keep the `@loader_path`-relative dynamic link. The only hard requirement is that the
absolute venv path in the spike's rpath does not survive.
